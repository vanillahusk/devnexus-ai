# 资源与运行边界

本项目主要在 WSL 中开发，曾因多 JVM、可观测性组件和持续写盘造成卡顿或连接中断。任何运行操作都必须有边界。

## 默认策略

- 默认不启动 Docker、Java 服务、中间件、监控栈或后台常驻任务。
- 能用静态检查、单元测试或已有日志回答的问题，不启动真实依赖。
- 不因依赖缺失自动拉起服务；明确报告缺失项和未验证范围。
- 用户说“先别启动”“暂停”或“停掉”后，不再启动任何进程，只允许执行必要的只读状态检查或用户明确要求的清理。

## 启动前检查

运行真实链路前必须明确：

1. 本次要证明的结论和成功条件。
2. 必需端口、服务和凭据；先做快速依赖预检。
3. CPU、内存、磁盘和 JVM 数量预算。
4. 最大运行时间、日志位置、结果位置和清理方式。
5. 当前已有进程，避免重复启动或误杀用户进程。

依赖预检失败时立即失败并记录具体原因，不继续启动下游 Java 服务。

## 有界运行

- 前台命令必须设置合理超时，禁止无期限等待。
- 长任务应由可追踪的后台任务执行，启动命令快速退出，并写入 PID、状态、日志和结果路径。
- 后台状态至少区分：运行、成功且已清理、失败且已清理、取消且已清理。
- 等待或轮询应低频、有限次；不得持续高频刷新日志或指标。
- 四个 JVM 场景继续串行启动并限制堆内存；不并行拉起整个微服务栈。
- 本地验证降低文件日志级别，降低 SkyWalking 采样率，限制 Prometheus 保留时间和抓取频率。
- 一次性 Prometheus、SkyWalking 或压测数据优先使用临时存储，任务结束后清理。

## 写盘控制

- 禁止无上限日志、Trace、指标和压测结果写入。
- 日志按本次证据所需保留，避免 DEBUG/TRACE 长期开启。
- Prometheus 本地抓取周期默认不短于 15 秒，并设置有限保留时间。
- SkyWalking 只采集验证所需流量；不为等待数据而制造持续请求。
- 发现异常写盘、内存上涨或 WSL 不稳定时，先停止本次任务并清理，再分析原因。

## 清理边界

- 只停止本次任务创建且可确认归属的进程、容器和临时文件。
- 不使用模糊进程名批量杀进程，不影响用户原有服务。
- 无论成功、失败还是中断，都应执行清理并记录清理结果。
- 交付前检查是否仍有本次启动的 JVM、容器、后台循环或监听端口。
