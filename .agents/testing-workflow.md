# 测试与证据工作流

测试的目标是支持准确结论，而不是只获得绿色输出。始终选择与改动风险匹配的最低充分验证等级。

## 证据等级

| 等级 | 验证方式 | 可以支持的结论 |
| --- | --- | --- |
| L0 | 语法、配置、格式和静态检查 | 文件结构与配置基本有效 |
| L1 | 纯单元测试、Mock、内存替身 | 分支逻辑和接口契约按预期执行 |
| L2 | Spring 组件测试或进程内集成测试 | 组件装配和本地协作正确 |
| L3 | MySQL、Redis、RocketMQ、Ragent 等真实依赖集成测试 | 指定真实依赖链路在当前环境跑通 |
| L4 | 端到端、故障演练、并发或压测 | 性能、恢复和最终一致性的实测结论 |

高等级可以包含低等级，但不能反向替代。Mock RocketMQ 通过不能表述为“RocketMQ 链路已验证”，编译成功不能表述为“功能已完成”。

## 执行顺序

1. 明确本次风险：接口契约、事务、并发、消息、数据迁移、资源或配置。
2. 先运行 L0 和最小范围的 L1/L2，失败时不扩大测试范围。
3. 只有任务验收标准或用户明确要求真实验证时才进入 L3/L4，并遵守资源边界。
4. 真实集成测试使用显式开关和依赖预检；依赖缺失时跳过或失败原因必须清晰，不能自动启动整套环境。
5. 修复后重跑直接失败项，再决定是否需要模块回归或全量回归。

## 结果记录

交付时精确记录：

- 执行的命令和测试范围。
- 通过、失败、跳过和超时数量。
- 使用真实依赖还是 Mock，以及依赖版本或端口。
- 未执行项及原因。
- 是否遗留服务、容器或测试数据。

跳过不是通过；偶发重试后通过也要说明首次失败原因，不能用重复运行掩盖不稳定性。

## 专项验证

- 事务：至少覆盖提交、回滚，以及业务数据与 Outbox 的原子性。
- 消息：至少覆盖重复、失败重试、死信和重放；原样重放复用事件 ID，修改 payload 的修正重放使用新事件 ID 并保留原事件关联 ID。
- MQ 与 Redis 双重缓冲：分别覆盖入队后数据丢失、MQ 重投与 Redis 残留、数据库提交后 Redis ACK 失败、processing 向 retry/dead 转移中断，并验证数据库级幂等。
- 状态与通知：分别乱序投递点赞/取消事件，验证事实状态和通知投影都只接受最新业务版本。
- Outbox 顺序：构造低版本失败退避、高版本先成功、低版本后到，验证消费者不会发生状态回退。
- RAG 全量重建：重建期间持续写入增量事件，验证追平水位后才能切换，新索引不会覆盖重建期间产生的新版本。
- 并发：覆盖多实例抢占、幂等竞争和乱序保护。
- RAG：固定数据集、固定指标和可重复基线，区分检索质量与生成质量。
- 压测：记录环境、数据规模、请求量、吞吐、P95/P99、错误率、积压、数据库变化和恢复时间。
- 故障演练：记录注入方式、可见现象、自动恢复、人工处理和最终一致性结果。
