# 后端可靠性规则

本项目的消息主线为 RocketMQ。可靠性目标是至少一次投递下的业务最终一致，而不是无法证明的“绝对不重复”。

## 统一设计口径

- 业务写入与 Outbox 事件在同一本地事务中提交或回滚。
- 调度器通过条件更新抢占待发送事件，支持多实例并发。
- 发送失败采用有界指数退避，超过阈值进入死信，支持查询、修正和人工重放。
- RocketMQ 可能重复投递；消费者以稳定事件 ID 和业务约束实现幂等。
- 消费成功后业务结果只生效一次，但基础设施层仍允许消息重复发送或重复到达。
- 原样重试/重放保持同一事件 ID；人工修改 payload 或业务语义的“修正重放”生成新事件 ID，并通过 `originalEventId`/`causationId` 关联原失败事件。
- 乱序场景使用业务版本、状态机或条件更新，不能只依赖到达顺序。
- 对账任务修复 Redis、MySQL、Outbox 或下游索引之间的最终不一致。

## 异步边界收敛

- 一个业务写入链路默认只保留一个承担削峰和可靠投递职责的持久化异步边界，避免无必要的 MQ → Redis → 数据库双重缓冲。
- 如果 RocketMQ 消费者在写入 Redis 后就返回，必须明确此时 Broker 已可能 ACK；不能把尚未进入事实库的数据描述为已经落库。
- 确需双重缓冲时，原始 `eventId` 必须贯穿 MQ、Redis processing/retry/dead 和 MySQL，数据库还必须有业务唯一约束或消费记录。
- 必须定义 Redis 入队失败由谁重试、Redis 数据丢失如何恢复、数据库提交后 Redis ACK 失败如何去重，以及 processing → retry/dead 转移的原子性。
- Redis 缓冲、幂等键和队列持久化策略必须写清楚，但 Redis 持久化配置不能替代数据库级幂等。
- MySQL 是评论等核心业务数据的唯一事实源；Redis 只能是缓存、待处理命令或派生投影，三种角色不得混用。

## 状态与通知分离

- 点赞状态与点赞通知是两个模型：MySQL 中的用户点赞状态是事实，Outbox/RocketMQ 只传播通知或下游事件。
- 状态事件必须包含期望状态和单调业务版本；数据库、通知投影、搜索索引等所有可变下游都要拒绝旧版本覆盖新版本。
- 不能只保证状态表乱序安全，而让通知端按照到达顺序执行“新增/删除”；通知端必须持久化最后处理版本并使用条件更新。
- 对账方向必须唯一且明确，例如 MySQL → Redis；对账前检查在途事件，不能用旧缓存反向覆盖最新事实。
- 重复点赞、取消点赞、重试和人工重放分别使用稳定事件 ID 去重，使用业务版本解决不同事件之间的乱序，两者不能互相替代。

## 重试、重放与修正

- 自动重试和未修改 payload 的人工重放仍是同一个逻辑事件，复用 `eventId`，消费幂等状态必须允许失败事件再次进入处理。
- 修改 payload、操作类型、业务版本或目标资源后，属于新的修正事件：使用新 `eventId`，并记录 `originalEventId`、修正原因、操作者和时间。
- `eventId` 解决同一事件重复执行，`businessKey + businessVersion` 解决不同事件乱序；不能为了绕过幂等随意换 ID，也不能为了追溯关系让修正事件复用已完成 ID。
- DLQ 管理接口必须区分“原样重放”和“修正后重新发布”，并保留完整审计关系。

## Outbox 顺序与租约

- Outbox 只承诺至少一次最终投递，不承诺只投递一次或全局顺序。
- 同一聚合的可变状态事件必须携带 `aggregateId + businessVersion`；指数退避导致旧事件晚到时由消费者拒绝旧版本。
- 多实例抢占必须使用条件更新和可过期租约。可以使用显式 lease 字段，也可以使用可验证的状态时间戳恢复，但实例宕机后不得永久停留在处理中。
- 错误字段保存错误码和脱敏摘要，不保存完整异常请求、正文或消息 payload。

## 微服务同步边界

- Gateway 普通请求优先本地校验签名 Token 和过期时间；不得让每个请求都无条件同步依赖 Auth Service。
- 强制登出和权限实时变化使用低成本的黑名单、Token 版本或有界缓存；确需远程校验时必须有超时、熔断和明确失败策略。
- 点赞、评论等主业务创建通知时使用本地事务 Outbox → RocketMQ → Message Service，不能以同步 Feign 创建通知作为主路径。
- Feign 用于确实需要同步结果的查询或管理操作，不能把非核心下游故障传播到核心写入事务。

## 每次改动必须检查

1. 正常路径是否闭环。
2. 事务中断、Broker 不可用、消费者失败时数据停在哪里。
3. 应用重启和依赖恢复后如何自动继续。
4. 重复、并发和乱序是否会造成二次副作用或旧状态覆盖。
5. 失败是否可观察、可定位、可重试、可死信、可人工恢复。
6. 多实例调度和消费是否存在重复抢占或锁永久占用。
7. 是否叠加了两个异步缓冲；若是，第二层带来的收益是否足以覆盖 ACK、持久化和去重复杂度。
8. 状态与通知是否共用同一到达顺序假设；每个下游投影是否独立执行版本比较。
9. 当前操作是原样重试还是内容修正；事件 ID 和因果关联 ID 是否使用正确。
10. 是否把可异步的跨服务副作用放进了核心同步调用链。

## 事件模型约束

- 使用统一事件信封，包含事件 ID、事件类型、Schema 版本、发生时间和业务主键；可变状态事件还必须包含业务版本。
- 修正事件增加原事件/因果关联 ID；事件 ID、Schema 版本和业务版本含义不得混用。
- 状态使用枚举或明确状态机，不散落魔法数字。
- 事件演进保持向后兼容；消费者明确处理或拒绝未知版本。
- 日志记录事件 ID 和关键状态，不打印完整敏感消息体。
- 不新增 RabbitMQ 依赖、配置、健康检查或双轨消费者。

## 可观测性

- Outbox 至少观察 pending、retry、dead、发送成功/失败、重试次数和恢复耗时。
- 消费端至少观察成功、重复、重试、死信、处理延迟和积压。
- 指标标签避免用户 ID、文章 ID、事件 ID 等高基数字段。
- 告警必须能对应处理动作，例如查看死信、恢复依赖或执行重放。

## 验证口径

- 单元测试证明幂等和状态机逻辑，不证明真实 Broker 可用。
- 集成测试覆盖本地事务提交与回滚、重复事件和并发条件更新。
- 真实 RocketMQ 验证覆盖生产、消费、重试/DLQ、重放和恢复。
- 双重缓冲链路必须注入四个故障窗口：Redis 入队后丢失、MQ 重投时 Redis 已残留、数据库提交后队列 ACK 失败、retry/dead 转移中断。
- 状态通知链路必须以“点赞 → 取消”和“取消 → 点赞”的正序、逆序、重复及重放组合验证最终通知投影。
- DLQ 同时验证原样重放仍受同一事件幂等保护，以及修正事件使用新 ID 后不会被原完成记录误拦截。
- 技术说明使用“至少一次投递 + 幂等消费 + 对账修复实现最终一致性”，不承诺端到端 exactly-once。
